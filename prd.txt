# Product Requirements Document (PRD)
# DuoChat — Private Peer-to-Peer Messaging

**Version:** 2.0  
**Status:** Ready for OpenCode implementation  
**Product type:** Private messaging application  
**Platforms:** Android and Windows desktop  
**Primary users:** Exactly two authorized people  
**Operating budget:** ₹0 target, using free-tier services  
**Availability target:** 24/7 cloud service, with direct peer-to-peer communication during eligible server outages

---

# 1. Product vision

DuoChat is a private messaging application designed exclusively for two people: the owner and their invited friend.

The application provides Android and desktop clients that share one conversation, synchronize message history, and support real-time messaging.

Its defining feature is **server-outage resilience**. When the main cloud messaging service becomes unavailable, the two users should still be able to communicate directly over the internet whenever a peer-to-peer connection is available.

The application must not depend on either user's computer or phone acting as a permanent server.

## 1.1 Core principles

1. Only two explicitly authorized accounts can access the conversation.
2. Android and desktop applications share the same identity and conversation.
3. Cloud messaging is the normal operating mode.
4. Direct peer-to-peer messaging is available when a valid connection can be established.
5. An existing peer-to-peer connection must not require the primary server to remain available.
6. Messages must be stored locally and queued safely when no connection exists.
7. Messages must synchronize when connectivity returns.
8. The project must target zero operating cost without silently enabling paid services.
9. Security and privacy must be enforced by the system, not merely by the UI.
10. All limitations of serverless connectivity, background execution, and free-tier hosting must be documented honestly.

# 2. Goals and non-goals

## 2.1 Goals

- Build a native Android messaging application.
- Build an installable Windows desktop application.
- Support communication across different Wi-Fi networks and mobile data connections.
- Support direct peer-to-peer text messaging using WebRTC.
- Continue an established direct connection if the primary signaling or messaging server fails, provided the connection remains usable.
- Support an alternative method for establishing connections when the primary signaling service is unavailable.
- Maintain persistent local message history.
- Synchronize messages across devices and recover after outages.
- Provide notifications on supported devices.
- Restrict the conversation to the two authorized people.
- Provide a reproducible build and deployment process through OpenCode.

## 2.2 Non-goals for version 1

Do not implement the following unless explicitly approved:

- Group chats.
- Public registration or a public user directory.
- Audio or video calling.
- Social feeds or stories.
- AI bots.
- Payments or subscriptions.
- Advertising.
- Multiple independent conversations.
- Large file transfers.
- Cloud-based message search across unlimited history.
- Mandatory paid TURN relays.
- Guaranteed delivery while both users are offline.
- Guaranteed connectivity when every available signaling and relay path is unavailable.

# 3. User scenarios

### Scenario A: Normal messaging

Both users are online and the cloud backend is available.

1. User A opens DuoChat.
2. User A sends a message.
3. The cloud backend accepts and persists the message.
4. User B receives the message in real time.
5. Both users see the same conversation history.

### Scenario B: Different networks

User A is on home Wi-Fi and User B is on mobile data.

1. The applications discover each other through an available signaling mechanism.
2. The clients establish an authenticated WebRTC connection.
3. Text messages travel directly between the clients when direct connectivity succeeds.
4. If a direct connection is impossible, the app falls back to cloud messaging when available.

### Scenario C: Main server becomes unavailable

Both clients already have an established peer-to-peer connection.

1. DuoChat detects that the cloud service is unavailable.
2. The application keeps the existing peer-to-peer connection alive where possible.
3. Messages are transmitted directly between the devices.
4. Each client stores sent and received messages locally.
5. The UI shows that the connection is direct and cloud synchronization is unavailable.
6. When the cloud service returns, the clients reconcile and synchronize message history.

### Scenario D: Server outage before connection establishment

The users are on different networks, and neither has an active direct connection.

1. The app detects that the primary signaling service is unavailable.
2. The app tries any configured secondary signaling mechanism.
3. If automatic discovery fails, the UI offers a manual connection setup method, such as exchanging a one-time connection QR code or connection data.
4. The app verifies the other user's identity before accepting the connection.
5. If no valid signaling path or manual exchange is available, the app explains that a connection cannot currently be established.

The application must not claim that WebRTC can automatically discover a remote peer without a signaling mechanism or another viable discovery path.

### Scenario E: Both users are offline

1. The sender composes a message.
2. The app stores the message locally.
3. The message remains marked as queued.
4. When a connection becomes available, the app attempts delivery.
5. The UI must distinguish queued, sent, delivered, and read states.

# 4. Platform requirements

## 4.1 Android

- Native Android application using Kotlin and Jetpack Compose.
- Target Android 10 (API 29) or newer, subject to library compatibility and current Android requirements.
- Support modern Android versions and common screen sizes.
- Generate a debug APK for development.
- Provide release APK or Android App Bundle build instructions.
- Support Android notification permissions.
- Store sensitive local data securely.
- Support dark and light themes.
- Handle network changes and app lifecycle events.
- Use supported Android background-execution mechanisms.
- Provide reconnection when the app resumes or network connectivity returns.

**Background limitation:** Android may suspend an application, restrict background network activity, or terminate a process. Do not promise uninterrupted peer-to-peer connectivity while the app is suspended or force-stopped.

## 4.2 Desktop

- Windows 10/11 support, subject to current framework compatibility.
- Tauri 2 with TypeScript and React.
- Installable desktop package.
- Desktop notifications where supported.
- Resizable window.
- Keyboard navigation.
- Secure local session persistence.
- Automatic reconnection after network changes.
- Clean application shutdown and recovery.

Keep the architecture extensible for Linux and macOS without delaying the first release.

# 5. Recommended architecture

Use a hybrid cloud and peer-to-peer architecture.

## 5.1 Technology stack

| Layer | Technology | Responsibility |
|---|---|---|
| Android client | Kotlin + Jetpack Compose | Native mobile interface |
| Desktop client | Tauri 2 + TypeScript + React | Desktop interface |
| Authentication | Firebase Authentication | Account identity |
| Cloud database | Cloud Firestore | Durable messages and synchronization |
| Cloud signaling | Firestore-based signaling or another supported signaling service | Connection negotiation |
| Peer transport | WebRTC DataChannels | Direct text messaging |
| NAT traversal | STUN | Peer connection establishment |
| Relay fallback | Optional TURN | Relay traffic when direct connections fail |
| Android notifications | Firebase Cloud Messaging | Background notifications |
| Local storage | Room on Android; SQLite on desktop | Local messages and delivery queue |
| Secret storage | Android Keystore and suitable OS credential storage | Sensitive local key material |
| Source control | Git | Versioning and reproducible development |

Before implementation, OpenCode must verify current official documentation, SDK compatibility, regional support, licensing, and free-tier limits.

### 5.2 System design

```text
                  CLOUD SERVICES
         ┌──────────────────────────┐
         │ Authentication           │
         │ Message persistence      │
         │ Primary signaling        │
         │ Push notifications       │
         └────────────┬─────────────┘
                      │
              Normal messaging
                      │
       ┌──────────────┴──────────────┐
       │                             │
┌──────▼────────┐             ┌──────▼────────┐
│ Android / PC  │◄───────────►│ Android / PC  │
│ User A        │ WebRTC P2P   │ User B        │
└───────────────┘             └───────────────┘
       │                             │
       └──────────────┬──────────────┘
                      │
             Local persistent queues
             and recovery mechanisms
```

The clients must support cloud messaging and peer-to-peer messaging as separate transports.

Do not require every message to pass through the primary cloud service.

# 6. Connection management

## 6.1 Connection modes

The application must implement the following states.

- `CLOUD_CONNECTED`
- `P2P_CONNECTED`
- `CLOUD_AND_P2P_CONNECTED`
- `CONNECTING`
- `RECONNECTING`
- `OFFLINE_QUEUED`
- `CONNECTION_FAILED`

The UI must display a clear connection indicator.

## 6.2 Normal cloud connection

When the backend is available:

1. Authenticate the user.
2. Load the private conversation.
3. Establish real-time synchronization.
4. Establish a peer connection when appropriate.
5. Maintain cloud persistence as the authoritative shared history.
6. Synchronize delivery and read state.

The implementation may choose cloud delivery as the initial default and peer-to-peer transport when appropriate. Avoid maintaining unnecessary duplicate connections when doing so would waste battery or resources.

## 6.3 Direct peer-to-peer connection

Use WebRTC DataChannels for direct text messaging.

Requirements:

- Support connection establishment across different networks where possible.
- Use ICE candidate gathering and connectivity checks.
- Use STUN servers for NAT traversal.
- Prefer direct paths where available.
- Detect disconnected or failed connections.
- Attempt reconnection after network changes.
- Resume cloud messaging when the backend is available.
- Preserve queued messages across reconnection attempts.
- Avoid duplicate message delivery.

## 6.4 Signaling requirements

WebRTC requires signaling to exchange session descriptions and ICE candidates.

The primary cloud signaling service may become unavailable. Therefore, the application must support a documented fallback strategy.

Implement the following in priority order:

1. Primary signaling service.
2. Optional secondary signaling service, only if a verified free solution is available and approved.
3. Manual one-time exchange of connection information through QR code or copy-and-paste, where technically supported.
4. Clear failure state when no viable signaling path is available.

Manual signaling data must be temporary, protected against replay where practical, and handled securely. The implementation must not treat a copied connection description as proof of identity.

The architecture must document whether a secondary signaling provider introduces an additional operational dependency.

## 6.5 STUN and TURN requirements

- Configure a STUN server for connection establishment.
- Do not hardcode a single unreliable public endpoint without documenting its limitations.
- Do not expose permanent TURN credentials in client source code.
- TURN must be optional and disabled by default if no free, suitable relay is available.
- Document that restrictive NATs, firewalls, carrier-grade NAT, and network policies may prevent direct connectivity.
- If TURN is unavailable, clearly explain that some connections may fail.

A TURN relay is not the same as the primary messaging server, but it is still an infrastructure dependency.

# 7. Functional requirements

## FR-01: Two-user access control

- Exactly two user identities are authorized.
- The owner explicitly configures both approved user IDs.
- The second user is approved through a secure setup process.
- Unapproved accounts cannot access the conversation.
- Unapproved users cannot read profiles or message metadata.
- Clients cannot create arbitrary conversations.
- Clients cannot change conversation membership.
- Authentication and authorization must be enforced by backend rules.
- A direct peer connection must also verify the peer's identity.

Do not rely on a secret URL or client-side visibility checks for access control.

## FR-02: Single private conversation

The initial release has one private conversation.

Features:

- Display names and avatars.
- Chronological message list.
- Sent and received message bubbles.
- Timestamps.
- Message history pagination.
- Empty state.
- Connection state.
- Retry for failed messages.
- Support for Android and desktop layouts.

## FR-03: Text messaging

- Send and receive text messages in real time.
- Maximum message length: 4,000 characters.
- Stable message IDs.
- Sender identity and timestamp.
- Duplicate detection.
- Retry support.
- Delivery state.
- Error feedback.
- Safe handling of unexpected input.

## FR-04: Local persistence

- Store conversation messages in a local database.
- Use Room on Android and SQLite on desktop.
- Keep messages available across ordinary application restarts.
- Encrypt sensitive locally stored data where appropriate.
- Queue outgoing messages when no transport is available.
- Retry queued messages when connectivity returns.
- Do not delete messages before the configured delivery and retention requirements are satisfied.
- Handle database migrations safely.

## FR-05: Cross-platform synchronization

- Both clients access the same logical conversation.
- Messages from Android appear on desktop.
- Messages from desktop appear on Android.
- Cloud history is restored after reinstalling, subject to authentication and backup availability.
- Messages exchanged directly during an outage synchronize after cloud recovery.
- Duplicate messages are deduplicated.
- Conflicting timestamps and out-of-order delivery are handled deterministically.

## FR-06: Delivery states

Implement these message states:

- `QUEUED`: stored locally but not confirmed as sent.
- `SENT`: accepted by the selected transport.
- `DELIVERED`: confirmed received by the recipient's application.
- `READ`: recipient has marked the message as read.
- `FAILED`: delivery attempt failed and requires retry or recovery.

The application must distinguish transport acceptance from recipient delivery. A successful local send does not mean the recipient has received the message.

## FR-07: Notifications

- Notify the recipient of incoming messages when supported.
- Respect Android notification permissions.
- Allow notification previews to be disabled.
- Avoid duplicate notifications for the same message.
- Open the correct conversation when a notification is tapped.
- Never expose administrative credentials.
- Do not claim that push notifications are guaranteed during a complete server outage.

Cloud push notifications depend on the notification service and network availability. Direct messaging must not depend on push notifications while both applications are actively connected.

## FR-08: Profiles

Each user can have:

- Display name.
- Profile picture or initials.
- Basic last-seen information, if supported.

Do not reveal unnecessary personal information.

## FR-09: Customization

- Custom application name and icon.
- Dark and light themes.
- Custom accent color.
- Consistent design across platforms.
- Responsive layouts.
- Accessible contrast and readable text.
- Connection status.
- Message delivery indicators.
- Loading, empty, offline, and error states.

## FR-10: Settings

Provide:

- Display name.
- Theme settings.
- Notification preferences.
- Connection mode and troubleshooting information.
- Sign-out.
- App version.
- Clear local cache option, with a warning if queued messages would be affected.

# 8. Data model

Use a consistent schema for cloud persistence and local storage.

## 8.1 Users

`users/{uid}`

Fields:

- `displayName`: string
- `photoURL`: optional string
- `createdAt`: server timestamp
- `lastSeenAt`: optional timestamp

Authorization data must not be editable by ordinary clients.

## 8.2 Conversation

`conversations/{conversationId}`

Fields:

- `memberIds`: exactly two approved user IDs
- `createdAt`: server timestamp
- `lastMessageAt`: server timestamp
- `lastMessagePreview`: optional string

The conversation ID must be fixed or deterministically configured.

## 8.3 Messages

`conversations/{conversationId}/messages/{messageId}`

Fields:

- `messageId`: globally unique stable identifier
- `senderId`: authenticated sender ID
- `text`: message content
- `createdAt`: server timestamp where available
- `clientCreatedAt`: local timestamp
- `type`: `text`
- `clientMessageId`: retry and deduplication identifier
- `transport`: cloud or peer-to-peer
- `deliveryState`: local delivery state

The backend must validate sender identity, message size, types, and allowed fields.

For peer-to-peer messages, the clients must preserve a consistent identifier so that later synchronization does not create duplicate cloud records.

## 8.4 Read states

`conversations/{conversationId}/readStates/{uid}`

Fields:

- `lastReadMessageId`: optional string
- `lastReadAt`: server timestamp where available

A user must only be able to update their own read state.

## 8.5 Local outbox

The local database must include an outbox table containing:

- `messageId`
- `recipientId`
- `payload`
- `createdAt`
- `attemptCount`
- `lastAttemptAt`
- `deliveryState`
- `lastError`

Sensitive message payloads must be protected at rest where appropriate.

Do not synchronize internal retry data as if it were a user-visible message.

# 9. Security and privacy

## 9.1 Authentication

- Use Firebase Authentication for cloud access.
- Maintain an explicit allowlist of the two approved accounts.
- Reject all other accounts.
- Do not automatically grant access after signup.
- Keep session handling secure.
- Support sign-out and credential revocation.

## 9.2 Database security

- Deny database access by default.
- Permit reads and writes only for approved members.
- Restrict message creation to the authenticated sender.
- Validate all message fields.
- Prevent users from modifying membership or authorization fields.
- Restrict profile access to the minimum required.
- Test security rules with authorized and unauthorized accounts.

## 9.3 Peer authentication

A direct WebRTC connection is not proof that the connected peer is the intended friend.

The implementation must:

- Bind each peer to an approved identity.
- Authenticate or cryptographically verify the peer.
- Reject unknown peers.
- Protect against replayed or forged connection data.
- Never trust a username or conversation ID alone.
- Document the identity-verification protocol.

If a complete secure identity protocol cannot be implemented in the initial milestone, direct connections must not be treated as trusted merely because they succeeded.

## 9.4 Encryption

- Use TLS for cloud communication.
- Use WebRTC's built-in secure transport for direct communication.
- Protect sensitive local data.
- Keep private keys and service credentials out of source control.
- Do not invent a custom cryptographic protocol.
- Do not claim end-to-end encryption unless the application implements and verifies it at the message layer.

Transport encryption protects data in transit, but it does not automatically protect messages from every party with authorized cloud access.

End-to-end encryption may be a future milestone using a reviewed protocol.

## 9.5 Secrets and configuration

- Provide `.env.example` or equivalent templates.
- Add local secret files to `.gitignore`.
- Never commit Firebase Admin credentials.
- Never place administrative credentials in Android or desktop clients.
- Do not expose permanent TURN credentials.
- Do not log message contents or authentication tokens.
- Document safe configuration and key rotation.

# 10. Availability and resilience

## 10.1 Availability goals

The service should be usable at any time, without requiring either user's personal device to act as a server.

The application must recover from:

- Temporary cloud outages.
- Wi-Fi disconnections.
- Mobile data changes.
- Desktop sleep and resume.
- Android application suspension.
- WebRTC connection failure.
- Signaling failure.
- Network changes.
- Duplicate or delayed message delivery.

No free provider or network architecture guarantees 100% uptime.

## 10.2 Outage behavior

When the cloud backend fails:

1. Detect the failure without blocking the interface.
2. Preserve local messages.
3. Keep an established direct connection alive where possible.
4. Continue direct delivery if the peer path remains available.
5. Attempt permitted alternative signaling when a new connection is required.
6. Queue messages when no path is available.
7. Display the current status clearly.
8. Synchronize after recovery.

## 10.3 Important limitation

If both users are on separate networks, have no active peer connection, and all signaling mechanisms are unavailable, the clients may be unable to discover and connect to each other.

This is a networking limitation, not a software bug that can always be eliminated.

The implementation must describe the limitation accurately and must not falsely promise universal serverless connectivity.

# 11. Free-tier requirements

The project targets ₹0 in ongoing operating costs.

- Use free-tier services where suitable.
- Do not require paid subscriptions for normal usage.
- Do not enable automatic billing or paid upgrades without explicit owner approval.
- Do not deploy paid services without approval.
- Verify quotas, regional availability, and current provider terms before deployment.
- Minimize database writes, polling, and unnecessary listeners.
- Document storage and bandwidth limits.
- Document TURN relay costs and availability.
- Document free-tier inactivity or suspension policies.
- Provide a cost review checklist.

If a requirement cannot be met within the free tier, OpenCode must explain the limitation and propose alternatives before changing the architecture.

Do not claim that free infrastructure guarantees 24/7 availability.

# 12. Performance requirements

Initial targets under normal network conditions:

- Active-client text delivery: approximately two seconds or less in typical conditions.
- Responsive interface while sending and receiving.
- Incremental message history loading.
- Reconnection without manual application restart when feasible.
- Efficient local message storage.
- Minimal unnecessary network and battery usage.

These are performance targets, not guaranteed delivery SLAs.

# 13. Testing requirements

## 13.1 Authentication tests

- Authorized user A can sign in.
- Authorized user B can sign in.
- Unapproved users are denied access.
- Unauthorized users cannot send or read messages.
- Unauthorized users cannot alter membership.
- Sign-out removes authenticated access.

## 13.2 Cloud messaging tests

- A sends a message and B receives it.
- B replies and A receives it.
- Messages persist after restart.
- Messages synchronize across Android and desktop.
- Failed messages can be retried.
- Duplicate cloud delivery does not create duplicate messages.

## 13.3 Peer-to-peer tests

- Both users establish a direct connection on the same local network.
- Both users establish a direct connection on different Wi-Fi networks.
- One user uses Wi-Fi while the other uses mobile data.
- An existing direct connection continues when the primary cloud signaling service fails.
- The application recovers after a temporary network change.
- Connection attempts fail safely when network restrictions prevent direct communication.
- The UI clearly indicates when no connection can be established.
- Unauthorized peers are rejected.
- Replayed connection data is rejected where applicable.

## 13.4 Recovery tests

- A sends messages during a cloud outage.
- The recipient receives messages through the direct path.
- Both clients retain local history.
- The cloud service recovers.
- Messages synchronize without duplicates.
- Message order remains consistent according to the documented policy.
- Unsent messages remain queued until delivery can be attempted.

## 13.5 Platform tests

- Android debug build succeeds.
- Android release build succeeds.
- Desktop development build succeeds.
- Desktop release package succeeds.
- Installation and startup work on clean supported devices.
- Android background restrictions are documented and tested.
- Desktop sleep and resume are tested.

## 13.6 Security tests

- Firestore rules deny unapproved access.
- Direct peers authenticate correctly.
- Secrets are not present in client bundles.
- Input validation rejects malformed messages.
- Local storage and session handling are reviewed.
- No security check is bypassed during outages.

# 18. Definition of done

The first release is complete when:

1. Two approved users can sign in.
2. Both can exchange persistent real-time text messages on Android and Windows.
3. The applications share a single conversation.
4. Messages are stored locally and in the cloud.
5. Direct messaging works across different networks whenever a valid peer connection is available.
6. An established direct connection can continue sending messages without the primary cloud signaling service, as long as the peer path remains available.
7. The application supports an alternative connection-establishment procedure when primary signaling is unavailable.
8. Messages queued during an outage synchronize after connectivity returns.
9. Unauthorized users cannot access the conversation.
10. The project builds reproducibly from documented instructions.
11. The implementation has been tested against the relevant failure scenarios.
12. Free-tier assumptions, security boundaries, and connectivity limitations are documented.

**Final product requirement:** Build a private Android and desktop messenger that normally uses cloud messaging but can communicate directly between the two authorized devices across different networks during eligible outages, with reliable local queues and synchronization after recovery. Never claim that direct communication is possible when no network path or connection-establishment mechanism exists.
